# OrbitWatch Project Audit

The project was reviewed from nine angles. Each finding is rated by severity and
marked **Fixed**, **Accepted** (a deliberate trade-off), or **Open** (future work).

| Severity | Meaning |
|---|---|
| High | Breaks the pipeline or creates a real security/stability problem |
| Medium | Works, but a reviewer or interviewer would flag it |
| Low | Polish or best practice |

## 1. Application code

| Sev | Finding | Status |
|---|---|---|
| Medium | **Unbounded metric labels.** Requests to unknown URLs were labeled with the raw path, so a bot scanning random URLs (`/.env`, `/wp-admin`, ...) would create a new Prometheus series for each one. Reproduced before fixing. | **Fixed:** unmatched routes share one `unmatched` label. |
| Medium | **Crashes weren't counted.** If a handler raised an exception, the metrics middleware never recorded it, so the error-rate panel would show 0% during an outage. | **Fixed:** middleware records the request in a `finally` block with status `500`. |
| Low | Kubernetes health probes (every 5–10s per pod) were mixed into request stats. | **Fixed:** `/healthz`, `/readyz`, `/metrics` excluded. |

## 2. Tests

| Sev | Finding | Status |
|---|---|---|
| Medium | No tests covered the metrics behavior above. | **Fixed:** added tests for unmatched-URL labels, probe exclusion, and crash counting. **9/9 pass.** |

## 3. Container image

| Sev | Finding | Status |
|---|---|---|
| Low | Base image `python:3.12-slim` is pinned by tag, not by digest, so it can change underneath you. | **Open:** pin `@sha256:...` once you've pulled it; Trivy now catches CVEs in the meantime. |
| Low | No Docker `HEALTHCHECK`. | **Accepted:** Kubernetes uses its own liveness/readiness probes; a Docker healthcheck is ignored there. |

Already good: multi-stage build, non-root UID 10001, no build tools in the final image, tests excluded via `.dockerignore`.

## 4. Kubernetes / Helm

| Sev | Finding | Status |
|---|---|---|
| Medium | The pod mounted a service account token it never uses, so an attacker who broke in would get Kubernetes credentials for free. | **Fixed:** `automountServiceAccountToken: false`. |
| Low | The PodDisruptionBudget (`minAvailable: 1`) was created even with a single replica, which would block node drains forever. | **Fixed:** only created when there are 2+ pods. |
| Low | All replicas could land on the same node. | **Fixed:** topology spread across nodes. |

Already good: requests/limits set, HPA, zero-downtime rolling updates, read-only root filesystem, all capabilities dropped, seccomp, passes the `restricted` Pod Security Standard.

## 5. Terraform

| Sev | Finding | Status |
|---|---|---|
| Medium | Grafana admin password was hardcoded (`change-me`) in a committed file. | **Fixed:** `sensitive` variable, or a random 24-character password generated by Terraform; passed via `set_sensitive` so it's hidden in plan output. |
| Low | Chart path was relative to wherever you ran Terraform from. | **Fixed:** resolved from `path.module`. |
| Low | The Grafana dashboard had to be applied by hand with `kubectl`. | **Fixed:** managed by Terraform as a ConfigMap. |

Already good: namespace quota + default limits, `depends_on` ordering, remote state with locking in CI, the AWS module restricts SSH/API to your IP with an encrypted disk and IMDSv2.

## 6. CI/CD pipeline

| Sev | Finding | Status |
|---|---|---|
| **High** | **`helm-lint` would fail on every run.** The `alpine/helm` image's entrypoint is `helm`, so GitLab couldn't start a shell in it. | **Fixed:** `entrypoint: [""]`. |
| Medium | No vulnerability scanning of the built image. | **Fixed:** Trivy job with a saved report. Set to warn rather than block, since new base-image CVEs appear over time. |
| Medium | Deploy jobs can't reach a cluster whose API only allows your IP, since GitLab's shared runners are on the public internet. | **Documented:** use a self-hosted GitLab Runner. Deploy jobs are skipped automatically until `KUBECONFIG_B64` is set, so the pipeline still goes green. |
| Low | Branch + merge request could run duplicate pipelines. | **Fixed:** `workflow:rules`. |
| Low | Kaniko's upstream project was archived in 2025. | **Documented:** still works; Buildah noted as the maintained alternative. |

Added: pip caching for faster test runs.

## 7. Air-gapped install

| Sev | Finding | Status |
|---|---|---|
| Medium | **The docs overclaimed.** Checksums were described as detecting tampering, but anyone who swaps a file can also swap the checksum list. | Low | The install script assumed helm/kubectl existed on the offline machine. | **Fixed:** checks for them up front with a clear error. **Open:** bundle the binaries themselves. |

## Version 0.2.0 additions

After the audit, three features were added to target space and defense platform work.

| Area | Added | How it was checked |
|---|---|---|
| Real orbits | SGP4 propagation from TLE data; TEME → ECEF → WGS-84 conversion; TLE age metric; CelesTrak update script | 4 satellites × 39 time points each match Skyfield within 0.02° lat/long and 0.5 km altitude |
| Pass prediction | `/passes` and `/stations` endpoints; AOS/TCA/LOS refined to ~1 s; max elevation and azimuths; input validation (≤72 h, mask 0–90°) | Every AOS/LOS is a true 10° crossing within ±2 s per Skyfield; peak elevation within 0.1°; pass counts match Skyfield. 72 h × 4 satellites computes in ~0.2 s |
| Zero-trust network | Default-deny NetworkPolicy; ingress only from same namespace + Prometheus; no egress | Template reviewed; **not yet run on a live cluster** |
| Supply chain | Syft SBOM (CycloneDX), cosign signature by digest + signed SBOM attestation, offline-verifiable (no transparency log) | CI structure validated; **jobs not yet run** |
| Admission control | Kyverno policy chart rejecting unsigned images, optional via Terraform | Template rendered to valid YAML in a manual check; Terraform parses |
| Air-gap delivery | Zarf package (`zarf/zarf.yaml`) + build script, optionally signed and with fresh TLEs | Script dry-run with a stubbed `zarf` binary; **real `zarf package create` not yet run** |

**Found during this work:** comparing pass times to Skyfield's `find_events()` showed a 7-second
gap on one pass. Checking elevation second by second showed our values matched Skyfield's own
`altaz()` to 0.0005°, and both crossed the mask at the same moment, so the gap came from
`find_events()` in this environment rather than our math. The test now verifies crossings
directly against Skyfield's elevation values.

**Found during live testing:** when a satellite was already overhead at the start of the
window, the pass was clipped to the window start without saying so. Passes now carry a
`started_before_window` flag (alongside `truncated` for the other end), with a test.

**Known limitations**
- Bundled TLEs are generated demo data (catalog 99901–99904), clearly labeled; run `scripts/update-tle.sh` for real satellites.
- Kyverno signature verification needs images to come from a registry (as with Zarf or the pipeline). The local `k3d image import` and the hand-rolled bundle's direct containerd import have no signatures to check, so keep the policy off for those.
- The NetworkPolicy assumes the network plugin allows kubelet probes (most do); `networkPolicy.extraIngress` is the escape hatch if not.

## What was verified, and what wasn't

**Verified in this workspace**
- Tests: 22/22 pass (API, metrics, and orbit/pass accuracy against Skyfield). Ruff lint: clean.
- App runs under uvicorn and serves telemetry, passes, and metrics.
- All shell scripts pass ShellCheck.
- Pipeline structure: every job's stage and `needs` reference is valid.
- All YAML, JSON, and Terraform (HCL) files parse.

**Not yet verified (network-blocked here; the GitLab pipeline checks these on the first push)**
- `docker build` of the image
- `helm lint` / `helm template` of the chart
- `terraform fmt -check` / `terraform validate`
- Syft, cosign, Kyverno, and Zarf against real infrastructure (tool versions are pinned in the pipeline)

If any of these fail on the first run, the error message will point to the exact line.
Fixing it yourself is great material for interview question 14.
